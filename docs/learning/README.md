# Concepts ollagi relies on

Short explanations, added as each step needs them. If a term in the code is unclear, it should be here.

## Decision records (`docs/decisions/`)

A decision record is a short note written when a choice is made: the situation, what was chosen,
why, and what it costs. Code shows *what* the system does; decision records keep *why*, which is
the part that gets lost. Each one is numbered and never rewritten: if a decision changes, a new
record says so and points back to the old one.

## The Python project layout

- `pyproject.toml` is the project's identity card: its name, version, the Python it needs, its
  dependencies, and `[project.scripts]`, which says "the command `ollagi` runs `main()` in
  `ollagi.cli`".
- `uv sync` reads it, creates `.venv/` (a private copy of Python plus our packages, so nothing is
  installed system-wide) and writes `uv.lock` with the exact version of every package.
- `uv run <cmd>` runs a command inside that environment, for example `uv run pytest` or
  `uv run ollagi --help`.
- `src/ollagi/` is the package. `tests/` holds tests that pytest finds by their `test_` prefix.

## /proc/meminfo and /proc/loadavg

- `/proc` is generated by the kernel on every read; it is how a program asks Linux about itself.
- `MemTotal` is all the RAM. `MemFree` is RAM nobody uses, which is usually small because Linux
  fills spare RAM with file cache. `MemAvailable` is the honest number: free RAM plus cache the
  kernel can drop at once. ollagi always uses `MemAvailable`.
- Load average (`/proc/loadavg`) is the average number of tasks running or waiting for a CPU. With
  8 CPU threads, a load of 8 means every thread is busy; above that, work queues up.
- The code parses the *text* of these files in pure functions, so tests can use sample text.

## Processes, parents and process trees

- Every running program is a process with a number (pid). Every process except the first has a
  parent (ppid): the process that started it. When Claude runs `dotnet test`, that `dotnet` is a
  child (or grandchild, through a shell) of the `claude` process.
- Following children from one process gives its process tree. ollagi counts a session's memory
  over its whole tree, because the builds and tests are usually heavier than `claude` itself.
- RSS (resident set size, `VmRSS` in `/proc/<pid>/status`) is the RAM a process holds right now.
  Shared libraries are counted in every process that uses them, so a tree's total is a little high.

## tmux

tmux runs programs inside a "server" that stays alive when you close the terminal. You can attach
to it later (`tmux -L <socket> attach`) and see the same screen. Two features make it useful from
code: `capture-pane -p` prints what is on the screen, and `send-keys` types into it as if you were
at the keyboard. `-L <name>` picks which server (socket) a command talks to.

## systemd scopes and cgroups

Linux groups processes into control groups (cgroups), folders under `/sys/fs/cgroup`. Each group
reports its memory (`memory.current` now, `memory.peak` the most it ever used) and can be frozen
(`cgroup.freeze`), which pauses every process in it without losing anything. systemd manages these
groups as units; `systemd-run --scope` puts a command we start into a new unit of its own.
`systemctl --user status ollagi-<name>.scope` shows one of ours.

## Fakes in tests

Code that runs outside programs (tmux, systemctl) takes the "run a command" function as a
parameter. Tests pass a fake that writes down the commands instead of running them, so they can
check *which* commands would run. One test still starts a real session, with a harmless shell
script instead of claude, to prove the real commands work together.

## Tailscale, MagicDNS and `tailscale serve`

- Tailscale joins my devices into a private network (a tailnet) over WireGuard, an encrypted tunnel.
  Each device gets an address like 100.x.y.z and a MagicDNS name like `omarchy.tail653118.ts.net`
  that only works inside the tailnet.
- `tailscale serve` makes a local server reachable on the tailnet: it receives requests on the
  device's tailnet address and forwards them to 127.0.0.1. It adds headers saying who sent the
  request (`Tailscale-User-Login`), which is how the page knows it is me.
- `tailscale funnel` would publish to the internet. ollagi never uses it.

## A systemd user service

A unit file (`deploy/ollagi.service`) tells systemd how to run a program: the command, what to do
if it crashes (`Restart=on-failure`) and when to start it (`WantedBy=default.target`, at login).
`systemctl --user` manages services that run as me, without root.

## Slices, and why tmux needed one (decision 0009)

A slice is a systemd group that holds other groups. Names nest by dashes: `app-ollagi-x.slice`
lives inside `app-ollagi.slice`, which lives inside `app.slice`. That is why session names escape
their dashes as `\x2d`.

tmux on this machine moves each program it starts into a scope of its own (`tmux-spawn-<id>.scope`),
but inside the slice the tmux server runs in. So the session's slice is the one group that holds
both tmux and Claude. Lesson: a test that only checked "memory is above zero" passed while measuring
the wrong thing; the test now checks a known amount (30 MiB).

## Freezing

`systemctl --user freeze <unit>` writes 1 to the group's `cgroup.freeze`: every process in it stops
being scheduled, keeps its memory and state, and continues on `thaw`. A frozen tmux cannot answer
either, so ollagi reads a frozen session's state from the group's files, never from tmux.

## Terminal colours (ANSI / SGR codes)

Terminals colour text with escape codes: `ESC[31m` means red, `ESC[1m` bold, `ESC[0m` back to
normal, `ESC[38;2;r;g;bm` an exact colour. `tmux capture-pane -e` keeps them. `static/ansi.js`
reads them one by one, keeps the current style, and wraps each run of text in a `<span>` styled
that way, always setting the text with `textContent` so nothing printed can run as code.

## SQLite, threads and a lock

SQLite is a database in one file, built into Python (`sqlite3`). The queue's server thread and the
web page's requests both use it, from different threads. Two threads inside one connection at the
same moment can break it, so every database method in `queue.py` takes a lock first
(`threading.RLock`): one thread at a time, the others wait their turn for a few microseconds.
